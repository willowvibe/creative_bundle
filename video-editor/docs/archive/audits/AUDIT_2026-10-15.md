# Video Editor Engine — System Design & Performance Audit

**Date:** 2026-10-15
**Baseline:** commit `be714fe` (`feat: vlog/tech CLI smoke tests + screen_to_video preset sentinel fix`)
**Scope:** Whole monorepo — architecture, render pipeline, performance on the target machine, redundancy/dead code, GPU utilisation, provider/model surface, and integration opportunities.
**Companion docs:** `docs/archive/plans/2026-10-15-render-graph-rewrite.md` (the P1 work plan), `docs/ARCHITECTURE.md`, `docs/ISSUES_BUGS.md`, `docs/ISSUES_BUGS.md`.

---

## 1. Executive Summary

The engine is a local-first AI video-editing monorepo: a Python workspace (`uv`) that orchestrates transcription, analysis, planning, FFmpeg transforms, generative assets, and skills; plus optional Node tooling (Remotion apps, bundled FableCut).

It works, but its **render model is the bottleneck**: every editing concern (cut, transitions, reframe, b-roll, graphics, captions, SFX, music) is a separate skill that *materialises its own intermediate MP4* by re-encoding. A single polished job therefore costs **4–9 sequential full-file encodes** plus `graphics`/`captions` each rendering **every segment separately** through HyperFrames and concatenating. On the target machine that dominates wall-clock time and compounds quality loss.

This audit locks in a direction: **rewrite the render path as a single render graph compiled to one composition**, make **HyperFrames the renderer**, keep **FableCut** as the human-edit surface, use the **4 GB GPU for ASR + NVENC only**, and keep **cloud generation** as the default. The full task breakdown is in the companion plan.

### Locked decisions (2026-10-15)

| Decision | Choice |
|---|---|
| Renderer | **HyperFrames is the renderer**; FFmpeg becomes the compile target + fallback. Retire the Remotion `apps/editor` / `apps/renderer` / `packages/remotion-types` stack. |
| FableCut | **Kept** as the human-editable timeline bridge (`ve preview` / `ve finalize`). |
| GPU (4 GB) | **ASR (`faster-whisper` large-v3-turbo, int8/float16)** + **NVENC encode/decode**. No resident vision models. |
| Generation | **Cloud-first** (PoYo / FAL / ElevenLabs / Sarvam). Local ComfyUI / ACE-Step / Whisper are offline fallbacks only. |
| Scope | **Full render-graph rewrite (P1).** |

## 2. Target machine profile

| Component | Value | Implication |
|---|---|---|
| CPU | AMD Ryzen 7 7735HS, 8C/16T, ~4.8 GHz | Adequate for x264 medium and CPU fallbacks |
| RAM | 30 GB (≈16 GB free) | Comfortable; watch concurrent Whisper + FFmpeg |
| GPU | NVIDIA RTX 3050 Laptop, **4 GB VRAM**, driver 580 | One model resident at a time; NVENC is free-ish (dedicated silicon) |
| Disk | 158 GB free (`/mnt/data2`) | Intermediate MP4s are expensive; render graph removes most |
| FFmpeg | **6.1.1** (Ubuntu apt) | Has `h264_nvenc`/`hevc_nvenc`/`av1_nvenc`/`libsvtav1`; **no `whisper` filter** (FFmpeg 8) |
| Python env | `faster_whisper` + `ctranslate2` present; **no `torch`, `whisperx`, `pyannote`, `scenedetect`, `cv2`** | WhisperX branch is dead here; vision/denoise need explicit installs |
| Node | Remotion 4 + FableCut (380 MB, gitignored) | Remotion stack is a retire candidate; FableCut stays |

**GPU doctrine (4 GB):**
1. **ASR is the primary GPU consumer.** `faster-whisper` `large-v3-turbo` at `int8_float16` uses ~1.5 GB VRAM and is ~4× faster than large-v3 / ~6× faster than current `small`-on-CPU, with better accuracy.
2. **NVENC for every non-final encode** (intermediates, previews, proxies). Dedicated hardware; near-zero VRAM.
3. **No resident vision models.** Reframe/scene-detection run on CPU with lightweight models (or in ComfyUI on demand), never co-resident with ASR.
4. **Serialise GPU work** behind a small scheduler so Whisper and ComfyUI never contend for VRAM.

## 3. Current architecture (as-is)

```
ve run
 ├─ TemplateRouter.select() → pipeline_kind
 ├─ storyteller   → build_storyteller_scene_plan → assets → Remotion render
 ├─ music_video   → build_music_video_plan → Remotion render
 ├─ <dir>         → apps/engine RawFootagePipeline   (v1: ingest→…→export)
 └─ <file/other>  → apps/cli SkillsPipeline (v2):
        rough_cut → [audio_cleanup] → [transitions] → [reframe] → [broll]
        → graphics → captions → [sfx_placement] → [sfx] → [music] → export
                    (each stage writes its own with_*.mp4)
```

* `graphics` builds a per-segment `CompositionPlan` and renders **each segment** via HyperFrames (or FFmpeg fallback), then concatenates.
* `captions` **re-renders every segment** with caption layers injected.
* `packages/core` holds the render cache, EDL/timeline, and the HyperFrames CLI wrapper.

## 4. Findings

### 4.1 Performance (ranked by impact)

| # | Finding | Evidence | Impact |
|---|---|---|---|
| P1 | **4–9 sequential full-file re-encodes per job.** Only `export` copies video. | `pipeline.py` stage chain; each skill emits `with_*.mp4` | Dominant wall-clock + generational quality loss |
| P2 | **`graphics` + `captions` render every segment separately** (2× N HyperFrames/FFmpeg renders + concats). | `graphics/renderer.py::render_all_segments`, `captions.py::_inject_captions_into_plan` | N× render overhead |
| P3 | **No GPU in encode or ASR.** `libx264 preset fast` on CPU; Whisper `small`/`base` on CPU. | `RenderOptions`, `whisper_local.py` (`device="cpu"`) | 4–6× ASR headroom wasted; CPU saturated by x264 |
| P4 | **`config.transcription` is dead config.** `engine/model/device/compute_type` parsed, never read. | No consumer of `TranscriptionConfig` | Misleading; keeps CPU defaults |
| P5 | **WhisperX branch is dead here** and there are two ASR paths. | `shutil.which("whisperx") is None`; `apps/transcribe` vs `packages/tools` | Dead code + divergent defaults |
| P6 | **Render cache re-hashes the whole source file** per key. | `render_cache._file_hash` on every `segment_cache_key` | O(filesize) per segment |
| P7 | **Sequential work**; only asset generation is concurrent. | `cut_segments` loop | Underuses 16 threads |
| P8 | **Three preview/render surfaces** (Remotion editor, Remotion renderer, FableCut) | `apps/editor`, `apps/renderer`, `packages/tools/FableCut` | Complexity + 380 MB + build surface |

### 4.3 Correctness / robustness

- `run_ffmpeg` captures unbounded stderr and logs full commands at INFO; no `-loglevel error`, no `-progress pipe:` streaming.
- No `-movflags +faststart`, no explicit `-pix_fmt yuv420p` on outputs.
- `BudgetGovernor` uses the legacy abstract **credit** table, not USD `pricing.yaml` (gating units are inconsistent with estimates).
- Provider default models are hand-synced across 4+ files (see 4.2).

### 4.4 Dev workflow

- **No CI** (`.github` only exists inside the gitignored FableCut clone), **no task runner**, **no benchmark harness**.
- Full test suite ~1451 tests / ~4.3 min single-process; no `pytest-xdist`.

### 4.5 HyperFrames integration (updated 2026-10-16: HTML path implemented)

The installed HyperFrames CLI is **v0.7.42**, which renders **HTML compositions**:

```
hyperframes render [DIR] [--composition/--output/--fps/--resolution/--gpu ...]
```

The repo's original `hyperframes_cli.render_segment` targeted an **older JSON-plan
interface** (`--input plan.json`) the CLI rejects ("Unknown flag: --input"), so the
`graphics` skill's HyperFrames path never actually executed, and the test suite
masks the binary via an autouse fixture (`tests/conftest.py::_hide_global_hyperframes_binary`).

**Implemented (M2b):** `video_editor_core.hyperframes_project.compile_hyperframes_project`
emits a real HTML composition (`index.html` + `assets/`, root `data-composition-id`
/`data-width`/`data-height`/`data-duration`/`data-fps`, base `<video>` plus one timed
`class="clip"` element per overlay on its own track), and
`hyperframes_cli.render_project` runs `hyperframes render <dir> -o out`. Verified
end-to-end: a 3 s graph composition rendered to a valid 1920×1080 MP4.

**Two constraints found:**

1. **Audio stays on FFmpeg.** HyperFrames rejects a video file used as an `<audio>`
   source ("composition asset does not match its authored media element type"), and it
   has no speech-aware ducking/loudnorm. The renderer therefore muxes the graph's mixed
   audio onto the rendered video with one FFmpeg pass (`compile_ffmpeg_mux_audio`, `-c:v copy`).
2. **HyperFrames is much slower here.** Rendering a 3 s overlay composition through
   Chrome took **~54 s**, versus **~1 s** for the FFmpeg single-pass — ~18× slower on
   this laptop (RTX 3050 / Ryzen 7). HyperFrames earns its cost on rich HTML motion
   compositions, not on simple cut + caption + overlay graphs.

**Consequence:** `render_graph` defaults to **`engine="ffmpeg"`**; `--render-engine
hyperframes` (or `auto`, which falls back to FFmpeg) selects the HTML path. Flipping the
default to HyperFrames (M2b step 4) is deferred pending a composition that justifies the
Chrome render cost.

**Script-to-video (M6.1):** `video_editor_core.scene_plan_composition` compiles a resolved
`ScenePlan` into an HTML composition (per-scene image/video/placeholder clips with Ken Burns
keyframes, narration `<audio>`, and the music bed) and renders it with HyperFrames —
including audio, so no separate mux. `MusicVideoPipeline` and `ve render` use it by default
(`render_engine=auto`) and fall back to the Remotion bundle; the Remotion stack is therefore
now a *fallback* and the `apps/editor` / `apps/renderer` / `packages/remotion-types`
deletion (M6.1) is unblocked.

### 4.6 Graphics plan layer schema

`graphics.models.Layer` uses a **`type`** field (not `kind`) and segment-relative timing. The render-graph builder must read `.type`; a first cut read `.kind` (via `getattr`), which silently turned base-video layers into empty text layers. Fixed; the builder skips base-video layers and uniquifies duplicate names (many `caption_line` layers) so HyperFrames lint passes.

## 5. Target architecture

### 5.1 Render graph (the core change)

Introduce `video_editor_core.render_graph`:

```
RenderGraph
 ├─ canvas:   width, height, fps, duration
 ├─ source:   primary source video
 ├─ cuts:     [Cut(source_start, source_end, timeline_start, timeline_end)]  (from the EDL)
 ├─ overlays: [Layer(kind=video|text|image|shape|logo, rect, timing, style, source, text)]
 ├─ audio:    [AudioTrack(kind=voiceover|music|sfx, source, start, gain_db, duck, loop)]
 └─ options:  codec / crf / preset / hwaccel / container
```

Skills become **plan contributors** — they emit `Cut`s, `Layer`s, and `AudioTrack`s instead of rendering files. Two compilers consume the graph:

- `compile_ffmpeg(graph) -> list[list[str]]` — **one** `filter_complex`: trim/concat → scale/pad → overlay layers (timed on the timeline) → audio buses (music with speech-aware duck, SFX, voiceover) → loudnorm → single encode. (A second pass only when two-pass loudnorm is requested.)
- `compile_hyperframes(graph) -> dict` — **one whole-timeline** HyperFrames composition plan (base video layer + timed overlay layers), replacing the per-segment plan.

`Renderer` selects HyperFrames when available, else FFmpeg. Either way the number of encodes drops from 4–9 to 1–2.

### 5.2 GPU pipeline

- Wire `config.transcription` → `faster-whisper` `large-v3-turbo`, `device: cuda`, `compute_type: int8_float16`, `small/cpu` fallback.
- `RenderOptions` gains `hwaccel` / `preset`; NVENC for non-final encodes.
- A `GpuScheduler` serialises ASR and ComfyUI; NVENC is exempt.

### 5.3 Single source of truth

`models.yaml` → generated `pricing.yaml`, `router.py` cost table, `estimate.py` map, `budget` rates, and template tier presets. One `make gen-models` (or `ve gen-models`).

### 5.4 Surfaces

- Renderer: **HyperFrames** (+ FFmpeg fallback).
- Human edit: **FableCut** via `ve preview` / `ve finalize`.
- Retire Remotion apps.
