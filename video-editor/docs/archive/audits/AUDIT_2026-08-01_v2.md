## 2. New Architecture & Design Issues

### N1. **CRITICAL — MCP server tools are stubs, not wired to the engine**

The MCP server (`packages/mcp_server/`) has 9 tool definitions but every
`call_*` function returns a static JSON response like `{"status": "queued"}`.
None of the tools actually invoke the engine. The `run_pipeline` tool doesn't
run a pipeline; `generate_image` doesn't generate an image.

**Impact:** The MCP server is non-functional. AI agents calling these tools
get fake responses. This is worse than not having an MCP server — it silently
lies to the caller.

**Fix:** Wire each tool to its corresponding engine function:
- `run_pipeline` → `SkillsPipeline.run_async()` or `ve run` subprocess
- `run_skill` → individual skill `run()` methods
- `generate_image` → `AssetIngestionManager.resolve()`
- `generate_tts` → TTS provider via manager
- `generate_music` → Music provider via manager
- `list_templates` → `TemplateRouter.list_templates()`
- `select_template` → `TemplateRouter.select()`
- `probe_media` → `probe_media()` from ffmpeg package
- `project_status` → `ProjectLedger` queries
- `cost_report` → `ProjectLedger` cost aggregation

### N2. **CRITICAL — `main.py` grew from 3,951 to 3,978 lines despite being flagged as critical**

The v1 audit identified `main.py` as a critical god-file needing immediate
split. Two months later it has 27 *more* lines. The `commands/` directory
was created but only holds `cache_prune.py` and `check_config.py` — the
remaining 40+ CLI commands, 30+ worker handlers, 15+ payload models, and
the worker loop all still live in `main.py`.

**Impact:** Same as v1 — merge conflicts, unmaintainable, too large for LLM
context windows.

**Fix:** Complete the split:
- `commands/ingest.py`, `commands/assets.py`, `commands/export.py`, etc.
- `handlers/ingest.py`, `handlers/run.py`, `handlers/assets.py`, etc.
- `payloads.py` — all Pydantic models
- `worker.py` — worker loop + handler registry

### N3. **HIGH — `test_cli.py` is still 3,555 lines with 76 test functions**

No progress on splitting this monolith. Every CLI change risks test conflicts.

**Fix:** Split into `tests/cli/test_ingest.py`, `tests/cli/test_assets.py`, etc.

### N4. **HIGH — No progress streaming or real-time observability**

Phase F (progress streaming) was planned but not started. Long-running
operations (music generation, video generation, full pipeline runs) block
with zero feedback. The MCP server's stub tools return `"status": "queued"`
with no way to track actual progress.

**Fix:** 
- Add SSE endpoint to MCP server for progress events
- Emit structured progress from every pipeline stage
- Build `ve watch <job-id>` command
- Surface progress in MCP tools as streaming results

### N5. **MEDIUM — Provider entry-point discovery not implemented**

Adding a new provider still requires touching 6 files. The v1 audit's
recommendation to use Python entry points for auto-discovery was not
implemented.

**Fix:** Use `pyproject.toml` `[project.entry-points."video_editor.providers"]`
for provider registration. The registry auto-discovers providers at import time.

### N6. **MEDIUM — No `[project.scripts]` entry points in pyproject.toml**

The CLI is invoked via `uv run ve` which works but is non-standard. There's
no `ve` console script registered, so `pip install` users can't run the CLI.

**Fix:** Add:
```toml
[project.scripts]
ve = "video_editor_cli.main:app"
video-editor-mcp = "video_editor_mcp.server:main"
```

### N7. **MEDIUM — Skills have `SkillProtocol` but don't consistently implement it**

`SkillProtocol` was added (J1) with `name` property and `run(ctx, **kwargs)`
signature. But looking at the actual skill implementations:
- `RoughCutSkill`, `GraphicsSkill`, `MusicSkill`, `ExportSkill` implement it
- `CaptionsSkill`, `SecondPassSkill`, `VerifySkill`, `PostRenderReviewSkill`
  have different signatures or don't declare the protocol

The pipeline (`SkillsPipeline`) imports skills directly by class, not through
the protocol. The protocol exists but isn't enforced or used for dispatch.

**Fix:** Have all skills explicitly implement `SkillProtocol`. Use the protocol
for dispatch in `SkillsPipeline.__init__` instead of hardcoded class references.

### N8. **LOW — `pipeline.py` still has hardcoded `DEFAULT_MUSIC_PATHS`**

Despite the v1 audit flagging this (B8), `pipeline.py` lines 56–60 still
hardcode `assets/music/default.{mp3,wav,m4a}` relative to `REPO_ROOT`.

**Fix:** Read from `config.yaml`'s `audio.default_music_path`.

### N9. **LOW — MCP server has no error handling or logging**

The MCP server's `call_pipeline_tool` and `call_asset_tool` functions have
no try/except, no logging, and return fake data. When wired to real engine
functions, any exception will crash the MCP server process.

**Fix:** Add try/except with structured error responses and logging.

## 3. New Bugs & Defects

### NB1. **HIGH — MCP server tools return fake data (integrity bug)**

Every MCP tool returns hardcoded JSON. `run_pipeline` always returns
`{"status": "queued"}` regardless of input. `generate_image` always returns
`{"status": "generated", "url": "https://example.com/image.png"}`. This is
not a stub — it's actively deceptive. An AI agent calling these tools will
make decisions based on fabricated results.

**Fix:** Wire tools to real engine functions (see N1).

### NB2. **MEDIUM — `PersistentJobQueue` has no WAL mode or connection pooling**

`PersistentJobQueue` opens a new SQLite connection for every operation
(`enqueue`, `dequeue`, `complete`, `fail`, `size`, etc.). Under concurrent
load from multiple worker tasks, this causes:
- SQLITE_BUSY errors when one connection holds a write lock
- No WAL mode (writers block readers)
- No connection pooling (expensive per-operation connect overhead)

**Fix:** 
- Enable WAL mode: `PRAGMA journal_mode=WAL`
- Use a single persistent connection (or connection pool) per queue instance
- Add `busy_timeout` pragma

### NB3. **MEDIUM — `PersistentJobQueue.dequeue` has no round-robin fairness**

`InMemoryJobQueue` implements per-tenant round-robin fairness. `PersistentJobQueue`
uses a simple `ORDER BY created_at ASC LIMIT 1` — a high-volume tenant can
starve others. The two queue implementations have different fairness guarantees.

**Fix:** Implement round-robin in `PersistentJobQueue` by tracking last-served
tenant in a separate table or using a cursor-based approach.

### NB4. **MEDIUM — `PersistentJobQueue` has no exponential backoff for retries**

`InMemoryJobQueue` implements exponential backoff (1s, 2s, 4s, ... capped at
60s) via `_delayed` and `available_at`. `PersistentJobQueue.fail()` immediately
resets the job to `status='pending'` with no delay. A failing job will be
retried instantly, potentially hammering a failing provider.

**Fix:** Add `retry_after` timestamp column. `dequeue` should skip jobs where
`retry_after > now`. `fail` should set `retry_after = now + backoff(retries)`.

### NB5. **MEDIUM — `AssetIngestionManager` has no cache size tracking**

The `ve cache-prune` command was added (B4 fix) but the manager doesn't track
total cache size. The prune command must scan the entire cache directory to
compute size, which is O(n) on every run.

**Fix:** Maintain a `cache_size_bytes` counter in the manager. Increment on
cache write, decrement on eviction. Persist to a `.cache_manifest.json`.

### NB6. **LOW — `_CLOUD_PROVIDER_LIMITS` in manager.py is missing new providers**

The concurrency limit dict (`manager.py` lines 38–51) doesn't include:
- `poyo_music` (no limit → unbounded)
- `sarvam_tts` (no limit → unbounded)
- `kitten_tts` (no limit → unbounded, but local so fine)
- `moss_tts` (no limit → unbounded, but local so fine)
- `ace_step` (no limit → unbounded)
- `coverr` (no limit → unbounded)
- `mixkit` (no limit → unbounded)

New cloud providers default to `_DEFAULT_CLOUD_LIMIT = 3`, but this is
undocumented and easy to miss.

**Fix:** Add explicit entries for all cloud providers. Add a test that
asserts every registered provider has a concurrency limit.

### NB7. **LOW — `_warn_in_memory_queue_once` is still not thread-safe**

Despite the v1 audit flagging this (B7), the global `_in_memory_warned` flag
is still a bare boolean with no lock. The `PersistentJobQueue` exists now,
so the in-memory warning is less critical, but the race condition remains.

**Fix:** Use `threading.Lock` or remove the warning now that `PersistentJobQueue`
is the recommended backend.

### NB8. **LOW — `_load_dotenv` is called at module import time**

`main.py` line 171 calls `_load_dotenv()` at module level. This means:
- Importing `main` (e.g., for testing) loads `.env` as a side effect
- The `.env` file path is hardcoded to `parents[4]` from `__file__`
- If the module is imported from a different location, the path is wrong

**Fix:** Move `_load_dotenv()` into a Typer callback or `app()` entry point.
Use `REPO_ROOT` from `constants.py` instead of `parents[4]`.

## 5. New Tools & Features from Internet Research

### T1. **MCP server ecosystem has exploded**

The v1 audit identified 4 MCP video servers. The 2026 landscape now shows:

| Tool | Tools | License | Key Feature |
|------|-------|---------|-------------|
| **Kinocut** | 142 | Apache 2.0 | Guardrailed FFmpeg, C2PA, video rescue, procedural audio |
| **VEMCP** | — | MIT | Pipeline FFmpeg, CUDA, VST3 plugins, EDL export |
| **video-creator-mcp** | 31 | — | Hyperframes + FFmpeg, multi-source downloads |
| **Video MCP** | — | Apache 2.0 | Kling/Veo/ElevenLabs, script-to-reel |
| **VidMCP** | — | MIT | SAM mattes, talking-head polish, smart cut |

Our MCP server (9 stub tools) is far behind Kinocut's 142 working tools.
The gap is not just tool count — Kinocut has guardrails, preflight validation,
quality checkpoints, and C2PA provenance that we lack entirely.

**Recommendation:** Study Kinocut's architecture for:
- Preflight validation pattern (validate inputs before running FFmpeg)
- Quality checkpoint system (verify output at each stage)
- C2PA provenance integration
- Tool granularity (one tool per atomic operation)

### T2. **Browser-based editing is production-ready**

**Timeline Studio** (MIT, 301 stars) runs entirely in the browser with
ONNX/WebGPU: Kokoro TTS, Whisper captions, Stable Audio 3 music, YOLOS+MODNet
smart framing, JoyVASA talking avatars. PWA-installable, fully offline.

**Vlo** (AGPL-3.0) is a ComfyUI-backed timeline editor with SAM2 masking,
video inpainting, keyframe+spline editor, and text-to-video generation.

**Recommendation:** Evaluate Timeline Studio's ONNX-in-browser approach for
a zero-install preview mode. Its Kokoro + Whisper + Stable Audio pipeline
is a subset of what we already do server-side.

### T3. **AI-native NLEs are maturing**

**AI Video Editor** (MIT) uses Remotion 4 + React 19 for motion graphics
with LLM-authored custom TSX components on demand. MCP server with 50+ tools.

**OpenCut AI** (MIT, 167 stars) is a full CapCut/Descript replacement with
edit-by-text, voice cloning, AI music, 9 video gen models, Docker deployment.

**Recommendation:** Study AI Video Editor's "LLM-authored custom components"
pattern — having the LLM write new Remotion TSX infographics on demand is a
capability we could add to our engine's graphics skill.

### T4. **Happy Horse 1.0 — joint video + audio generation**

Happy Horse 1.0 (15B params, open-source) generates synchronized video AND
audio together — not separate generation stitched later. 1080p cinematic
quality, 7-language lip-sync, ~38s for 5s/1080p on H100.

**Recommendation:** This is a fundamentally different approach from our
current "generate video, generate audio, mix them" pipeline. Evaluate for
scenes where tight audio-video sync matters (musical performances, dialogue).

## 6. Testing & Quality Gaps

### TQ1. **HIGH — No tests for MCP server tools**

The MCP server has zero tests. `test_mcp_server.py` exists but only tests
tool listing, not actual tool execution. When the stubs are replaced with
real engine calls, there will be no safety net.

**Fix:** Add `tests/test_mcp_server.py` with:
- Test each tool with valid inputs
- Test each tool with invalid/missing inputs
- Test error handling
- Test concurrent tool calls

### TQ2. **HIGH — No tests for `PersistentJobQueue`**

`test_queue.py` tests `InMemoryJobQueue` extensively but has no tests for
`PersistentJobQueue`. The SQLite backend is untested.

**Fix:** Add `TestPersistentJobQueue` class to `test_queue.py` with:
- Basic enqueue/dequeue/complete/fail
- Multi-tenant isolation
- Stale job requeue
- Concurrent access from multiple tasks
- Schema migration (add column, existing DB still works)

### TQ3. **MEDIUM — No integration tests between MCP server and engine**

Even after wiring MCP tools to the engine, there are no tests that verify
the integration works end-to-end.

**Fix:** Add `tests/test_mcp_integration.py` that:
- Starts the MCP server
- Calls each tool
- Verifies the engine actually executed the requested operation

### TQ4. **MEDIUM — No tests for `PersistentJobQueue` retry/backoff behavior**

`InMemoryJobQueue` has exponential backoff. `PersistentJobQueue` doesn't.
When backoff is added (NB4), it needs tests.

**Fix:** Add tests for:
- Retry with increasing delays
- Max retries → dead letter
- Retry after backoff expiry

### TQ5. **LOW — No tests for `ve cache-prune` with actual cache data**

`test_cli_cache_prune.py` exists but may use mocked cache directories.

**Fix:** Add test that:
- Creates real cache files with known sizes
- Runs `ve cache-prune --max-size-gb 0.1`
- Verifies old/large files are evicted
- Verifies recent/small files are kept

### TQ6. **LOW — No performance regression tests**

Still not addressed from v1 audit (C2/T6).
