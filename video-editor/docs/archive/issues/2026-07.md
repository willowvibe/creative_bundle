- [x] #28 `worker()` reached into private `queue._completed` /

### Audit findings (Session K Part 2)

A fresh audit of the changed surface (`main.py`, `queue.py`,
`pipeline.py`, enqueue payload contract) surfaced 4 issues worth
filing. None are showstoppers, but #27 is a real usability gap now
that the worker actually consumes payloads.

- [x] **#27 — `ve enqueue` payload contract is undocumented.** With
  the worker now real, the JSON payload that `enqueue <command>
  --payload '{...}'` accepts determines what the worker actually
  runs. Today the supported keys are scattered across
  `_handle_*` functions in `main.py` and the user has no way to
  discover them short of reading the source. Fix: add a per-command
  key table to `docs/CLI_USAGE.md` (or `README.md`) listing the
  supported payload keys for every command the worker understands
  (e.g. `analyze` → `{force, config_path}`, `run` →
  `{source, transcript, preset, brand, ...}`).

  **Session L:** added `docs/CLI_USAGE.md` with a per-command key
  table covering all 16 worker handlers, the common
  `work_root`/`output_root` keys, the `edit` SegmentEdit schema,
  the `force` flag, `preset`/`presets_dir`, and `broll_provider`.
  The `enqueue` command's docstring points users to the new doc;
  `README.md` links to it from the CLI Commands section.

- [x] **#28 — Worker reports progress via private queue state.**
  The `worker()` loop tracks processed/failed counts by snapshotting
  `len(queue._completed)` / `len(queue._failed)` before and after
  each dispatch, then diffing. The `_completed` / `_failed`
  attributes are private (underscore-prefixed); this couples the
  CLI to a queue implementation detail and would break the moment
  we swap the in-memory queue for a persistent backend. Fix: add
  `pending_count()`, `completed_count()`, `failed_count()` (or
  similar) to the `JobQueue` ABC and have the worker call those.

  **Session L:** added public `pending_count()`,
  `completed_count()`, `failed_count()` to the `JobQueue` ABC
  and `InMemoryJobQueue` impl. `worker()` now calls the public
  API. 8 regression tests in
  `tests/test_queue.py::TestPublicCountMethods`. A persistent
  backend can implement the same methods (e.g. as SQL
  `COUNT(*)`) without changing the dispatcher.

- [x] **#29 — `ctx.ensure_dirs()` called on every dispatch.** Each
  handler invocation triggers a stat/mkdir pass on `work_root` /
  `output_root`. For a worker draining 100 jobs against the same
  context that all already ensured their dirs, that's 200 extra
  syscalls per drain. Fix: ensure once at the top of the worker
  loop (per `JobContext`) and skip per-handler.

  **Session L:** extracted ctx construction into
  `_build_job_context` and moved `ensure_dirs()` to the top of
  the worker loop. The dispatcher no longer calls it. Regression
  test in
  `tests/test_cli.py::test_worker_calls_ensure_dirs_once_per_dequeue_not_per_handler`
  patches the method with a counter and asserts it runs
  exactly N times for N jobs.

- [x] **#30 — `_handle_run` falls back to `/work` `/output` when
  payload omits `work_root`/`output_root`.** This is the legacy
  v1 path: the in-memory queue warning in `main.py` already tells
  users to prefer `--work-root`/`--output-root`. With the worker
  now real, a job that has no `work_root` in its payload will
  trigger `PermissionError` on most developer machines. Fix:
  document the contract (rolled into #27) and optionally add a
  loud warning when either key is missing from a `run` payload,
  matching the `--broll-provider` warning pattern from Session C.

  **Session L:** added a loud stderr warning in the worker loop
  (not just for `run` — for any command whose payload omits
  `work_root`/`output_root`). Warns once per missing key with
  the suggested `--payload` syntax. Regression tests cover
  both the warning-on and warning-off paths.

- [x] **#39** **Per-segment QA hook + pipeline QA gate.** Two
  pieces:

  **5a. Per-segment check.** New `QASelfEvalError` exception
  in `skills/qa/src/qa/models.py` carrying `segment_id`,
  `reason` (``"visual_jump"`` or ``"audio_pop"``), and the

  `check_segment_boundary(prev_path, curr_path, ...)` that
  runs two ffmpeg invocations on the join: a `psnr`

### Architecture note

The flow in `SkillsPipeline.run`:

```
captions_video → sfx_input = self._generate_and_mix_sfx(captions_video)
                  ↓
                 (when sfx_provider set, also produces
                  broll/with_broll_sfx.mp4 and sfx/sN.mp3)
                  ↓
music.run(input_video=sfx_input) → music/with_music.mp4
                  ↓
export.run → final.mp4
```

`_generate_and_mix_sfx` reads `<work>/plan/scene_plan.json`,
calls `sfx_requests_for_scene` per scene, resolves them via
`AssetIngestionManager` (cache-honored), writes
`<work>/sfx/<scene_id>.mp3`, then calls `mix_sfx_into_video`
with a `(path, start_time)` timeline built from cumulative
scene durations.

The SFX-mixed video is written to
`<work>/broll/with_broll_sfx.mp4` (not
`<work>/sfx/with_broll_sfx.mp4`) because it reuses the broll
directory to colocate all intermediate video artifacts.

form_data: dict[str, str] = {"text": text, "with_alignment": "true"}

  `<work>/<job_id>/transcript/transcript.json`. The helper
  is a no-op when `transcript.json` already exists (a
  pre-existing transcript wins — never clobber a
  known-good file) and returns `False` when the
  alignment file is also missing. The function also
  stamps the manifest with
  `stages.transcribe.outputs.source = "alignment"` so
  downstream consumers (and human readers of the
  manifest) can tell where the transcript came from.
- `RoughCut.run()` gained a third branch in its
  transcript-resolution priority ladder:
  1. **user-supplied** `transcript_path` — copied verbatim.
  2. **alignment** (Session V + W) — converted from
     `transcript/alignment.json`.
  3. **WhisperX fallback** — the existing behavior.
- `skills/rough_cut/pyproject.toml` gained
  `video-editor-asset-ingestion` as a dependency.

### Why the priority order is "user > alignment > WhisperX"

This is the contract a user can reason about:

- `--transcript <path>` always wins — explicit > implicit.
- `ve align` is a deliberate preprocessing step the user
  paid for (a free ElevenLabs API call) and they expect
  those timestamps to drive the pipeline.
- WhisperX is the slow, expensive fallback (~30s of GPU
  per minute of audio) — only when nothing better exists.

The "user > alignment" case is the most important: a user
who hand-edited `transcript.json` after running `ve align`
and then ran `ve run` should not have their hand-edits
silently overwritten by a stale alignment JSON.

### Test design notes

The four tests in
`tests/test_rough_cut.py::TestRoughCutAlignmentPromotion`
are organized to lock down the priority order one branch
at a time. The "transcript wins" test calls the helper
directly rather than going through `run()` — this avoids
the ambiguity of the test that pre-stages both files and
then expects the existing transcript to be preserved,
since the current `run()` semantics are "an existing
transcript.json gets re-transcribed on the next run"
(intentionally — `run()` is the "do everything fresh"
entry point, not "resume from where I left off"). The
helper is the unit at which the priority contract lives.

### No bugs filed

The implementation went green after one test
redesign — the original `test_transcript_takes_precedence_over_alignment`
went through the full `run()` flow and discovered that
`run()`'s contract is "re-transcribe on every call,"
not "preserve existing transcript." This wasn't a bug
in the new code; it was a mismatch between the test's
expectation and the existing pipeline semantics. Fixing
the test (helper-direct assertion) was the right move —
resuming from a prior transcript is a separate feature,
not something Session W needed to deliver.

### Issue D — `sidechaincompress` silently outputs `[0:a]` when its key label is fanned out [x] REAL BUG

**Status:** Fixed. This is a real bug, not a false
diagnosis. The earlier "disproof" (a 2-input test where the
sidechain key label was NOT fanned out) missed the actual
trigger.

**Symptom:** When the same filter pad label is used both as
the `sidechaincompress` key AND as an input to another
filter (e.g. `amix`), ffmpeg fails silently. With
multi-char labels it errors `Invalid stream specifier: vo`;
with single-char labels it does NOT error but **silently
falls back to outputting input `[0:a]`** (the source
video's own audio). The "mix" is then the source's audio,
not the VO — exactly what happened to the Saju final.mp4:
the second-pass "fix" hit -17.5 LUFS but the audio was the
seq test-tones at -32 dB, with ZERO voiceover in it.

**Repro (the broken graph):**
```
[1:a]volume=2.5,alimiter=limit=0.95,aresample=44100[a];
[2:a]volume=-16dB,aresample=44100[b];
[b][a]sidechaincompress=...[c];       # [a] fanned out as key here
[a][c]amix=inputs=2...[d]              # AND as amix input here -> [d] = [0:a]
```
Probing each stage: `[a]` = VO at -10.9 dB (correct), but
`amix([a],[c])` = -32.5 dB = `[0:a]` exactly, with no VO
peaks (max -17.5 dB vs `[a]`'s 0 dB).

**Fix:** give the sidechain its own copy of the VO via
`asplit=2` so the label is never fanned out:
```
[1:a]volume=1.0,alimiter=limit=0.90,aresample=44100,asplit=2[vo][vokey];
[2:a]volume=-14dB,aresample=44100[mus];
[mus][vokey]sidechaincompress=threshold=0.02:ratio=6:attack=10:release=400:makeup=1[musduck];
[vo][musduck]amix=inputs=2:weights=1 1:normalize=0:duration=first[mix];
[mix]alimiter=limit=0.90[out]
```
Also `amix=normalize=0` to disable amix's auto-attenuation
(see Issue F). Verified in the Saju final: first-10s mean
-14 dB / max 0 dB (VO present) vs the broken -32 dB /
-17.5 dB; integrated -12.9 LUFS, true peak 0.1 dBFS.

**Engine impact:** None. `mix_background_music`
(`skills/music/src/music/mix.py`) already uses
`[0:a]asplit=2[spk][ref]` — the sidechain key (`[ref]`) and
the mix input (`[spk]`→`[spk_out]`) are separate asplit
outputs, so no label is fanned out. The bug only affected
the user-written `saju_finalize.py`, now fixed.

### Issue F — Audio level bug in Saju final composition [x]

**Status:** Fixed in both the user production script and
the engine's `mix_background_music`.

**Symptom (before fix):** After applying Issues A-E fixes
via `/home/harish/Videos/saju/saju_finalize.py`, the
resulting `final.mp4` was ~16 dB quieter than either input
alone. Spectrum analysis (ffmpeg `astats`):

| File                    | Peak (dB) | Avg (dB) |
|-------------------------|-----------|----------|
| `voiceover.mp3` (alone) | -14       | -15      |
| `generated_music.mp3`   | -15       | -18      |
| **`final.mp4` (broken)**| **-30**   | **-33**  |

**Two compounding causes:**

1. `amix=inputs=2` does RMS-normalization by default —
   splits unity gain between the two inputs. VO at -14 dB
   becomes ~-20 dB after amix. Use `weights=2 1` to give
   VO 2x weight, and/or boost the VO post-sidechain with
   `volume=` before amix.
2. The previous sidechain was too aggressive
   (`threshold=0.1:ratio=15:attack=50:release=300`),
   pushing music to near-silence under continuous speech
   and only partially recovering in 300 ms. Soften to
   `ratio=8:release=500`.

**Engine fix** (`skills/music/src/music/mix.py`):
`mix_background_music` gained `speech_makeup: float = 2.0`
and `limiter_ceiling: float = 0.95` params. The filter graph
now applies `volume=speech_makeup,alimiter=limit=limiter_ceiling`
to the speech branch and `amix=inputs=2:weights=2 1` so the
speech dominates instead of being RMS-averaged to
half-amplitude. Regression test:
`tests/test_music.py::test_music_mix_preserves_speech_loudness`
(failed RED at exactly 6.0 dB attenuation before the fix;
passes GREEN within ±4 dB after).

**Production script fix**
(`/home/harish/Videos/saju/saju_finalize.py:178-187`):
the Step 2 filter graph mirrors the engine fix —
`volume=4.0` makeup on the VO branch + `alimiter=limit=0.95`
ceiling + softer sidechain (`ratio=8`, `release=500`,
`threshold=0.05`, `makeup=2`) + `amix=weights=2 1`.

**Measured result (after fix):** The second-pass numbers
(max RMS -11.9 dB, true peak -2.8 dBFS, integrated
-17.5 LUFS) turned out to be measuring the SEQ test-tones,
not the VO — see Issue D. After the asplit fix (Issue D),
the Saju final was re-measured with the VO actually present:
first-10s mean -14.0 dB / max 0 dB, integrated -12.9 LUFS,
true peak 0.1 dBFS (no clipping). Music was then raised
from -18 dB to -14 dB (≈ +50%) at the user's request — VO
still dominant (-14 dB mean, 0 dB peaks), music clearly
audible during pauses (-13 dB bed), no clipping. The
engine's `mix_background_music` (Issue F fix:
`speech_makeup` + `limiter_ceiling` + `weights=2 1`) was
never affected by the Issue D fan-out bug because it uses
`asplit` for the speech/key split.

## 2026-07-12: Suryastakam musical-video build (#227, #228)

The Suryastakam build (`videos/2026-07-12/suryastakam/suryastakam_final.mp4`,
180.0s, 1920×1080, hero music `Sri_Suryashtakam_2026-07-05T055930.mp3`,
4 PNGs + 5 MP4 clips as fillers, 23 lower-bottom pop-style Hindi captions)

real media had not previously touched.

- [x] #227 — `scripts/compose_musical_video.py` zoompan `x=` expression
  uses runtime-only `z` variable that FFmpeg 6.1+ rejects
  (`x_expr = f"({pan_start}+({pan_end}-{pan_start})*on/{frames})*(iw-iw/z)"`,
  ~line 153). FFmpeg 6.1 validates the static expression form before
  runtime and rejects `z` as an undefined constant
  ("Undefined constant or missing '(' in 'z)'"). On every real-image
  render the first `Parsed_zoompan_*` fails, ffmpeg exits 0 frames
  written, the build silently produces a zero-byte output. Earlier
  FFmpeg (and synthetic stub images) let this pass; the 727-test suite
  never exercises a real PNG, so the regression was uncaught.
  **Found 2026-07-12 during Suryastakam build (user's first real-image
  musical-video request).**

  Fixed 2026-07-12: rewrote `x_expr` to express the pan in input pixels
  using only `on`/`d` and the pre-computed start/end scale values (no `z`
  reference). The new formula is math bit-equivalent to the old for all
  4 motion indices (verified by numeric simulation:
  `pan_start = -pan_delta * (1.0 - 1.0 / start_scale)` for `zoom_in` and
  the mirror for `zoom_out`; offset = `pan_start_factor * iw` in input
  pixels). All 4 cases match within 1e-3 px. See the
  `suryastakam-zoompan-bug-2026-07-12.md` memory for the full derivation.

  **Regression test TODO (next session):** generate a real PNG with
  PIL at known size (e.g. 1280×720) and assert that the composer
  produces a non-zero `ffprobe` output. The current
  `test_compose_musical_video.py` suite uses synthetic stubs and would
  not have caught this. The user's intent was clearly to use real
  imagery; we need at least one end-to-end "real PNG → real MP4" test
  in the suite.

- [x] #228 — Initial Suryastakam caption pass collapses multi-line
  verses into a single caption with a space, visually clipping the
  second line. The inline parser in the prior build session used a
  `current[]` accumulator that joined every non-header line of a verse
  with `" "`, so the 2-line verse
  "आदिदेव नमस्तुभ्यं प्रसीद मम भास्कर ।" + "दिवाकर नमस्तुभ्यं प्रभाकर नमोऽस्तुते ॥ 1 ॥"

### Design lessons from the Suryastakam build

1. **Real media is the only way to catch the 6.1-vs-earlier-FFmpeg
   regression class.** Stubs and mocks hide ffmpeg behavior changes;
   every musical-video test should end-to-end render with at least
   one real PNG/MP4 fixture.

2. **Lyric files are line-structured, not verse-structured.** Any
   parser that groups lines into "blocks" risks hiding the line
   boundaries that verse formatting relies on. The invariant "one
   caption per source line" is the only safe default for verse
   texts.

3. **The composer + post-process split is paying off.** Two
   independent steps (compose visuals+audio, then burn captions)
   means a caption change is a 3-minute re-render instead of a
   3-minute + 19-xfade re-render. The pattern (composer → SFX,
   composer → captions, composer → voiceover) is the right shape
   for all future musical-video variants.

4. **The hero-music-only invariant is the user's hard requirement
   for devotional content.** See `musical-video-hero-audio-preference`
   in memory. The composer enforces this by mapping only the music
   input's audio (`-map 19:a` in the 19-input case), so original
   clip audio never reaches the output regardless of media content.

5. **The "phased + slow" preference generalizes:** 50% slower
   transitions, 50% video speed, halved Ken Burns amplitude. All
   three are encoded in the composer's defaults. See
   `musical-video-motion-speed-feedback` in memory.
